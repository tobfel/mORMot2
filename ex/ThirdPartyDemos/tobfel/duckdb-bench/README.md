# dbbench - DuckDB vs SQLite3 vs PostgreSQL for analytics

`dbbench` runs the same analytical queries on DuckDB, SQLite3 and PostgreSQL,
all through the `mormot.db.sql` classes, so the numbers are what a mORMot
application gets.

It answers two questions:
- when does DuckDB pay off compared with the usual mORMot storage engines?
- how much SQL does each engine need for typical analytics?

## The data: TPC-H

[TPC-H](https://www.tpc.org/tpch/) is the reference benchmark for analytical
(decision support) databases: 8 tables of a wholesale supplier (orders,
line items, customers, parts, suppliers, nations, regions) and 22 queries.

- **Reproducible:** the data is generated by DuckDB itself (`CALL dbgen(sf = 1)`),
  without any download, and is the same on every computer.
- **Scalable:** scale factor 1 is 6 million `lineitem` rows (about 1 GB of CSV),
  10 is 60 million rows, and so on.
- **Comparable:** DuckDB, PostgreSQL, ClickHouse and many papers publish TPC-H
  numbers. For a broader comparison of engines including SQLite and PostgreSQL,
  see also [ClickBench](https://benchmark.clickhouse.com/) (100 million rows of
  web analytics).

`dbbench --prepare` generates the data with DuckDB, then copies it into SQLite3
and PostgreSQL via DuckDB `ATTACH (TYPE sqlite)` and `ATTACH (TYPE postgres)`,
so all engines hold exactly the same rows.

## The queries

All queries fetch all their rows. The numbers of each result are summed and
compared between the engines: a `*` in the results marks a different result.

| file | what | why |
|---|---|---|
| `q01` | TPC-H Q1, 8 aggregates over 98% of `lineitem` | full scan |
| `q03`, `q10` | TPC-H joins of 3-4 tables with top N | join and sort |
| `q05` | TPC-H 6-table join over one year | join order |
| `q06` | TPC-H selective range, covered by an index | index-friendly |
| `q12`, `q14` | TPC-H joins with conditional aggregates | |
| `q18` | TPC-H group by over all `lineitem` in a sub-query | big hash aggregate |
| `a1` | monthly revenue and 3-month moving average | window over an aggregate |
| `a2` | top 3 customers per nation | top N per group |
| `a3` | median and 90th percentile per priority | percentiles |
| `a4` | revenue per year and ship mode | pivot table |
| `a5` | revenue per region and nation with subtotals | rollup |
| `a6` | most expensive order per priority | arg max |
| `a7` | distinct customers per year and segment | count distinct |
| `p1` | 10,000 point lookups by primary key | OLTP |
| `p2` | 10,000 single-row inserts in one transaction | OLTP |

`queries/xxx.sql` is the DuckDB SQL, `queries/xxx.pg.sql` and
`queries/xxx.sqlite.sql` override it when the dialect differs.
`p1` and `p2` use cached prepared statements, as the mORMot ORM does.

## The engines

| engine | what |
|---|---|
| `duckdb` | embedded DuckDB, file opened read-only |
| `sqlite` | embedded SQLite3 (statically linked by mORMot) |
| `postgres` | PostgreSQL server over libpq, on the same computer |
| `duckdb-sqlite` | DuckDB engine reading the **SQLite3 file** (`ATTACH ... (TYPE sqlite)`) |
| `duckdb-postgres` | DuckDB engine reading the **PostgreSQL tables** (`ATTACH ... (TYPE postgres)`) |
| `quack` | a remote DuckDB server via the Quack protocol (`--quack` option) |

The two `duckdb-*` engines show the hybrid approach: the application keeps its
SQLite3 (e.g. the mORMot ORM) or PostgreSQL database for OLTP, and runs the
analytics with the DuckDB engine on the same data, with no migration.

## Indexes: best practice for each engine

- **SQLite3** (`sql/schema.sqlite.sql`, `sql/index.sqlite.sql`): `INTEGER PRIMARY KEY`
  (the rowid), composite key for `lineitem` and `partsupp`, one index per foreign
  key and per filtered date, a covering index for Q6, then `ANALYZE`.
  Connection settings: 8 KB pages, WAL, 2 GB page cache, 8 GB `mmap_size`,
  in-memory temporary storage.
- **PostgreSQL** (`sql/schema.pg.sql`, `sql/index.pg.sql`): `NUMERIC(15,2)` as in
  the TPC-H specification, `VARCHAR` instead of `CHAR(n)`, primary keys and the
  same secondary indexes created after the load, a covering index for Q6
  (`INCLUDE`), then `VACUUM ANALYZE` for the statistics and the index-only scans.
  Server settings in [PostgreSQL settings](#postgresql-settings).
- **DuckDB** (`sql/index.duckdb.sql`): no index for analytics. DuckDB stores
  min/max values per row group (zonemaps) and skips data with them. A primary key
  on `orders` is only there for the point lookups (`p1`).

## Running it

```
# PostgreSQL user, as in the defaults of dbbench
sudo -u postgres psql -c "create user bench password 'bench' superuser"

# compile dbbench.dpr with Delphi or FPC (64-bit for the embedded DuckDB),
# put libduckdb.so / duckdb.dll next to it, then:
./dbbench --prepare --sf 1 -d /data        # generate and load (once)
./dbbench --sf 1 -d /data --md sf1.md      # run all queries, 5 runs each
./dbbench --sf 1 -d /data -o q01,a3 -e duckdb,sqlite   # a subset
./dbbench --help
```

Each query runs once to warm the caches and check the result, then `--runs`
times (5 by default): the table shows the median. A warm-up longer than
`--maxseconds` (30 by default) is not repeated (`^` in the table).

`--prepare` installs the DuckDB `tpch`, `sqlite` and `postgres` extensions; use
`--extrepo https://extensions.duckdb.org` if plain HTTP is blocked.

### Remarks

- **Analytics:** DuckDB is 10 to 500 times faster than SQLite3, and 5 to 65 times
  faster than PostgreSQL, on 4 cores. SQLite3 is single-threaded and row-based;
  PostgreSQL uses up to 4 parallel workers, but reads full rows and computes on
  `NUMERIC` values.
- **Indexes help OLTP, not analytics:** the selective `q06` uses a covering index
  in SQLite3 and PostgreSQL, and is still 5 to 25 times slower than a DuckDB scan
  without index.
- **OLTP is the opposite:** a point lookup or a single insert costs 1 to 2 us
  with SQLite3, 60-70 us with PostgreSQL (one network round trip), and 0.6-0.9 ms
  with DuckDB. This is the DuckDB engine itself: the Python `duckdb` 2.0.0 module
  shows the same timing, so the mORMot driver is not the bottleneck.
- **Hybrid:** DuckDB reading the SQLite3 file (`duckdb-sqlite`), with no
  migration and no extra copy, is 2 to 100 times faster than SQLite3 on its own
  file for scans, aggregates and joins, but slower for the index-friendly `q06`
  and `q14`: the SQLite3 indexes are not used by DuckDB.
  DuckDB over PostgreSQL (`duckdb-postgres`) reads the tables with binary `COPY`:
  faster than PostgreSQL for the heavy queries (`a2`, `a3`, `a5`, `a6`, `a7`,
  `q18`), slower for the index-friendly ones.
- **Query tuning, as an experienced user would do** (see the comments in the
  `queries/*.pg.sql` / `*.sqlite.sql` files):
  - SQLite3 `q01`: the planner used the `l_shipdate` index for 98% of the rows
    (26 s). The unary `+l_shipdate` disables it: 17 s.
  - SQLite3 `q12`: `CROSS JOIN` forces scanning `lineitem` first, which is twice
    as fast.
  - PostgreSQL `a6`: `DISTINCT ON` sorts all the orders (7.6 s); a join with the
    `max()` per group takes 0.4 s.
  - PostgreSQL `a7`: `count(DISTINCT)` always sorts; a `DISTINCT` sub-query
    allows a parallel hash aggregate (5.4 s to 2 s).
  - DuckDB needed no tuning.

## SQL for analytics: DuckDB vs PostgreSQL vs SQLite3

The `a*` queries do the same thing on each engine; compare the files in
`queries/` to see the differences.

| need | DuckDB | PostgreSQL | SQLite3 |
|---|---|---|---|
| group by all non-aggregated columns | `GROUP BY ALL` | repeat the columns | repeat the columns |
| reuse a select alias | also in a window `ORDER BY` (`a1`) | `GROUP BY`, `ORDER BY` | `GROUP BY`, `ORDER BY` |
| top N per group (`a2`) | `QUALIFY row_number() OVER (...) <= 3` | sub-query + `WHERE rn <= 3` | sub-query + `WHERE rn <= 3` |
| median, percentiles (`a3`) | `median(x)`, `quantile_cont(x, 0.9)` | `percentile_cont(0.9) WITHIN GROUP (ORDER BY x)` | none by default: 2 windows + interpolation |
| pivot table (`a4`) | `PIVOT ... ON col IN (...) USING sum(x)` | `sum(x) FILTER (WHERE col = ...)` per column | `sum(x) FILTER (WHERE col = ...)` per column |
| subtotals (`a5`) | `GROUP BY ROLLUP / CUBE / GROUPING SETS` | `GROUP BY ROLLUP / CUBE / GROUPING SETS` | one `UNION ALL` per level |
| value at the maximum (`a6`) | `arg_max(key, value)` | `DISTINCT ON (...) ... ORDER BY` | bare column next to `max()` |
| closest previous row in time | `ASOF JOIN` | `LATERAL (... ORDER BY ... LIMIT 1)` | correlated sub-query |
| columns by pattern | `SELECT * EXCLUDE (a)`, `COLUMNS('price_.*')` | - | - |
| profile a table | `SUMMARIZE orders` | - | - |
| query files directly | `FROM 'data.parquet'`, `read_csv('https://...')` | extension or `COPY` | - |
| export | `COPY (SELECT ...) TO 'out.parquet'` | `COPY ... TO` (CSV/binary) | - |

## When DuckDB is the right tool

DuckDB is a column store with a vectorized, multi-threaded engine:

- **Use it for analytics:** aggregates, joins and window functions over millions
  of rows, reports, dashboards, data exports, ad-hoc exploration, Parquet/CSV
  files, and as a fast read-only copy of an OLTP database.
- **Keep SQLite3 or PostgreSQL for OLTP:** point lookups, single-row inserts and
  updates, many concurrent writers. Each DuckDB statement has a fixed cost of
  some hundred microseconds (`p1`, `p2`), SQLite3 needs a few microseconds.
- **Combine both:** keep the mORMot ORM on SQLite3 or PostgreSQL, and run the
  analytics with DuckDB `ATTACH` on the same data (`duckdb-sqlite`,
  `duckdb-postgres`), or copy the data to a DuckDB file or Parquet now and then.
